## Preguntas de cierre
1. ¿Por qué un token decodificable no necesariamente es un token válido?
Porque el formato JWT codifica sus partes (header y payload) en Base64Url sin cifrado, permitiendo que cualquiera lea los datos JSON. Sin embargo, un token solo es criptográficamente válido si su firma digital (la tercera sección) coincide al ser verificada con la clave secreta (HS256) y si no ha expirado ni violado emisor o audiencia.

2. ¿Cuándo corresponde responder 401 y cuándo 403?
- 401 (Unauthorized): Cuando la solicitud carece de credenciales de autenticación, el token está ausente, mal formado, expiró o la firma no coincide (falla de autenticación: "¿quién eres?").
- 403 (Forbidden): Cuando la identidad está verificada y el usuario es reconocido, pero su rol o privilegios no le permiten ejecutar la operación solicitada (falla de autorización: "¿qué puedes hacer?").

3. ¿Por qué CORS no sustituye la autenticación?
CORS es un mecanismo de seguridad impuesto exclusivamente por navegadores web para regular si una página en un origen puede leer respuestas de otro origen (Same-Origin Policy). No impide que clientes HTTP directos (como curl, Postman, scripts de backend o atacantes) envíen solicitudes ni comprueba la identidad o permisos del solicitante.

4. ¿Qué riesgo existe si DELETE se registra antes de requireRole?
Si la ruta o el controlador se ejecutara antes del middleware de autorización, la tarea sería eliminada de la base de datos antes de evaluar si el usuario cuenta con rol de administrador, dejando el recurso desprotegido frente a usuarios normales autenticados.

5. ¿Por qué debes iniciar sesión después de cambiar el rol en MongoDB?
Porque el rol está encapsulado dentro de los claims del payload del JWT que se firmó al momento del login. Como los JWTs son independientes (stateless), el servidor confía en la firma del token durante su vigencia (1h). Si el rol cambia en la base de datos, el token antiguo sigue teniendo role: 'user' hasta que expire o se genere un nuevo token con role: 'admin'.

6. ¿Cómo llega un error asíncrono de authenticate al errorHandler en Express 5?
authenticate es una función asíncrona que retorna Promise<void>. Si verifyAccessToken falla y lanza un AppError, Express 5 intercepta automáticamente la promesa rechazada de forma nativa y la envía directamente al middleware final errorHandler sin necesidad de envoltorios adicionales ni bloques try/catch.

7. ¿Qué limitación tiene el almacén en memoria del rate limiter al escalar la API?
El almacén en memoria (MemoryStore) mantiene el conteo de peticiones en la RAM del proceso local de Node.js. Si la API se escala horizontalmente en múltiples instancias, contenedores o detrás de un balanceador de carga, cada instancia llevará un contador independiente por IP, permitiendo multiplicar el número de intentos permitidos. Para producción a escala se debe usar un almacén distribuido compartido como Redis.

8. ¿Qué cambios requeriría autorizar por propietario de la tarea?
Requeriría modificar el esquema de persistencia TaskPersistence para incluir un campo userId: ObjectId que asocie cada tarea a su creador, migrar los documentos existentes, actualizar el servicio y repositorio para filtrar las consultas por userId (o permitir que el admin vea todas), y agregar una validación en las rutas de modificación y eliminación para comprobar que task.userId === auth.userId antes de proceder.

## Reflexión
El error que más me ayudó a comprender el flujo fue recibir 401 INVALID_AUTHORIZATION_HEADER al probar con un token sin el prefijo Bearer. Me permitió confirmar cómo el middleware descompone estrictamente el encabezado Authorization, exigiendo el formato estándar Bearer <token> antes de intentar validar la firma criptográfica con jose.
